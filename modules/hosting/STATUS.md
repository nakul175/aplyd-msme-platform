## Why a launcher, not a plain deployment

The application is a Cloudflare Worker with a D1 database (decision D-06). DigitalOcean has neither a Workers runtime nor D1. `scripts/serve.mjs` therefore runs the same built Worker (`dist/server`, from `pnpm build`) in workerd, the open-source runtime Workers use, through Miniflare, which the test layers already use. The database is Miniflare's D1: a SQLite file in the temporary directory (checked on 6 October 2026: it is not held in memory), in a new directory at every start, built from the migrations and the SYNTHETIC seed. In front of it sits a small gateway (`modules/hosting/src/gateway.ts`) that holds the access gate, answers the platform's health check, and hands every other request on.

```
browser --https--> platform ingress --http--> gateway (PORT, 0.0.0.0) --http--> workerd (127.0.0.1, APLYD_UPSTREAM_PORT)
                                                  gate, /healthz, size limit        the application, D1 (SQLite file)
```

## What it does

1. **Refuses to start** (exit code 2, every problem listed, the secret never printed) unless: `APLYD_ENV` is `local`, `synthetic` (the default) or `test`; `SESSION_SECRET` is at least 32 bytes, not one repeated character and not the spec's placeholder `REPLACE_ME`; and a gate is configured: `DEMO_USER` (no colon, not `REPLACE_ME`) and `DEMO_PASSWORD` (12 characters or more, not `REPLACE_ME`), or `DEMO_ACCESS=open` in so many words. Each of the three placeholders is refused on its own, by name (before 6 October 2026 a `DEMO_USER` left as `REPLACE_ME` started; review finding S3-05). Synthetic sign-in lets anyone who can reach the address sign in as any synthetic user, the operator included, so an ungated address is something the person deploying has to ask for.
2. **The gate.** HTTP Basic. User and password are compared as SHA-256 digests with `timingSafeEqual`. Without them every route but `/healthz` answers 401. The gate's `Authorization` header is removed before the request reaches the application, and so is every header whose name starts with `mf-`: Miniflare's own control headers (`MF-Original-URL`, `MF-CF-Blob`, `MF-Route-Override`), which its entry worker acts on, and which a client must not be able to set (review finding S3-04).
3. **`/healthz`** answers without the gate, for the platform's health check, and says `ok` (the application's own `/api/health` answered 200) or not (503, or "starting" while the database is built), then a second line `commit <id>` naming the git commit being run: from `APLYD_COMMIT` (7 to 64 hexadecimal characters; anything else is ignored and the launcher says so), or `commit unknown` when it is not set. On App Platform the value is `${_self.COMMIT_HASH}`, set as a run-time value in `.do/app.yaml`; for any other build, `--build-arg APLYD_COMMIT=$(git rev-parse HEAD)`. The commit is on this route only. It asks the application at most once every two seconds.
4. **Sign-in works behind a TLS-terminating ingress.** The application refuses a state-changing request whose Origin differs from the origin of the URL it is given (cross-site protection). Behind an ingress that URL is the launcher's own `http://` one, so an Origin whose host equals the request's Host is rewritten to the origin the application sees; every other Origin is passed on unchanged and the application refuses it. If the platform rewrites Host, `APLYD_PUBLIC_HOSTS` (comma-separated) names the public host names to treat as this site's own.
5. **A body over 256 KB is refused** (413), declared or streamed, before the application reads it. The application's own limit is 64 KB.
6. **Upgrade requests are closed**; hop-by-hop headers are not passed on; a down application is a plain 502 with no address or error text.
7. **Stops on SIGTERM and SIGINT**: the gateway closes, the Worker's process ends, exit code 0 (Miniflare's own handlers, which exit at once and leave workerd running, are replaced).
8. **A restart is a reset.** There is no way to keep data, by design: the tables are append-only (corrections are new rows), so a demonstration cannot be put back by deleting rows, and rebuilding the database is the only reset that is true to the model.
9. `APLYD_DEMO=true` is read by the launcher and, if `modules/demo/src/seed.ts` exists, calls its `seedDemo(baseUrl)` after the application is up (slice 9, pull request #11; run on 6 October 2026: 5 companies, 3 providers, 68 requests). Without that package the launcher stops with a message when `APLYD_DEMO=true`.
10. **Watchdog.** Once the application is ready, the launcher asks the Worker's own health route (`/api/health`, on loopback) every 5 seconds (`APLYD_WATCHDOG_SECONDS`). After 6 failed probes in a row (`APLYD_WATCHDOG_PROBES`; 0 turns it off), about 30 seconds, it logs one line and exits with code 1, so a platform that restarts a stopped container replaces a dead Worker. One good answer starts the count again. It does not run while the application is starting (`/healthz` says `starting`), and SIGTERM and SIGINT still stop the launcher with code 0.

## How to deploy it on DigitalOcean App Platform

What a person has to do, because it needs the account owner (sign-in, authorising DigitalOcean to read a private GitHub repository, choosing a region, accepting the cost, typing three secrets):

1. Sign in to DigitalOcean and create an app from GitHub: repository `nakul175/aplyd-msme-platform`, branch `main`. App Platform will find the `Dockerfile`. Authorising DigitalOcean's GitHub application for that repository is a step of this.
2. Or create it from the spec: `doctl apps create --spec .do/app.yaml`, or paste the file into the console's "Edit App Spec".
3. Choose a region and the container size. The spec says `apps-s-1vcpu-1gb-fixed` (1 GiB; see "Cost and size").
4. Set three encrypted run-time values, in place of `REPLACE_ME`: `SESSION_SECRET` (at least 32 random characters, for example `openssl rand -hex 32`), `DEMO_USER` and `DEMO_PASSWORD` (at least 12 characters). While any is still `REPLACE_ME` the container exits at start (the spec's own placeholders are refused by the launcher; a test pins this), so a deploy made too early fails and does not run open.
5. Deploy. The platform builds the image (install and build) and then starts the container; the spec's health check is `/healthz` (the live app uses the platform's default, per the sponsor's report). On the development machine the launcher was ready 2.2 seconds after starting without the demonstration and 5.3 to 8.0 seconds with it (6 October 2026, a clean copy; the earlier figure of about 12 seconds was taken on a busy machine); the platform's own start time was not measured. The first build on the platform took 2 minutes 11 seconds (the sponsor's report).
6. Open the app's address, give the gate's user and password, and use the application's own sign-in page.

To run the same thing on any machine with Node 22.18 or later: `pnpm install --frozen-lockfile && pnpm build`, then `SESSION_SECRET=… DEMO_USER=… DEMO_PASSWORD=… node scripts/serve.mjs` (it listens on `PORT`, default 8080).

## Cost and size

- DigitalOcean's App Platform pricing page, read on 5 October 2026 (not in `docs/sources.md`; check it again before relying on it): a fixed container with 1 vCPU and 512 MiB is $5.00 a month (`apps-s-1vcpu-0.5gb`) and one with 1 vCPU and 1 GiB is $10.00 a month (`apps-s-1vcpu-1gb-fixed`). The spec uses the second.
- Measured on the development machine on 6 October 2026, three runs of the launcher in a clean copy (`ps` resident set sizes, summed over the launcher's Node process and workerd): 306 to 345 MB at the highest during start, 273 to 300 MB after 60 seconds idle, 297 to 319 MB after a browse of the pages as two signed-in people. With the demonstration on, the Node process held about 150 to 220 MB and workerd about 125 to 145 MB. About 289 MB at the highest when shared pages are counted once. So the 1 GiB container has room (about a third used) [Certain for the processes on that machine; Likely on the platform, whose own overhead was not measured]. The 512 MiB size would probably hold but leaves little [Guessing]; the spec keeps 1 GiB.
- The build in the platform's own builder installs every dependency (the build and Miniflare are development dependencies) and builds the application; the platform's build time and memory were not measured.

## Not built, and limits

1. **Not production, and not for real patient or company data.** Synthetic sign-in is the only sign-in (OQ-13 is open). The gate is one shared password for everyone, with no per-person accounts, no lockout and no rate limit on attempts. A password of 12 characters is the least the launcher accepts; its strength is the deployer's choice. Anyone who has it can act as the operator and as every synthetic owner.
2. **Nothing is durable.** The database is a file in the container's temporary directory, new at every start. Any restart, redeploy or platform maintenance resets it, and anything a viewer entered is gone. The spec runs one instance, because a second would hold a different database.
3. **Between the platform's ingress and the container the traffic is plain HTTP**, including the gate's password. That leg is the platform's network. The browser's leg is the platform's HTTPS.
4. **The Dockerfile was not run under Docker by this module's authors, and the app spec has never been applied from this repository.** The sandbox has no container daemon, and Docker Hub is not reachable from it. On 6 October 2026 the Dockerfile's steps were run in a clean copy, without Docker: `corepack prepare`, `pnpm install --frozen-lockfile` (10 seconds, empty store), `pnpm build` (8 seconds), then the launcher with the Dockerfile's environment (VALIDATION.md). That does not exercise the image itself, the non-root user, or the platform's builder. The sponsor reports that the platform built it on 5 October 2026 in 2 minutes 11 seconds. A text test pins the files to the repository's own pins (pnpm, Node, no secrets) and checks that `.dockerignore` leaves `.env*`, `.dev.vars*`, `*.pem` and `*.key` out of the build context (S3-09: `COPY . .` would otherwise carry a developer's local `.dev.vars` into an image built from a working tree; a build from git never has the file); it is not a build. `.do/app.yaml` is a template for a new app: it differs from the live app in name, branch, autodeploy, region and health check (RUNBOOK section 5.2), and must not be applied to the live app.
5. **The platform's ingress is assumed**, not observed: that it forwards the browser's Host header, and that the health check goes to `/healthz` over HTTP on the container's port. If it rewrites Host, sign-in is refused as cross-site until `APLYD_PUBLIC_HOSTS` names the public host. The region was not chosen: the pages that list App Platform's regions did not give a table to this agent, and the one summary of them it saw did not list Bangalore; check the console.
6. **It is not Cloudflare.** The runtime is workerd, the same one Workers use, but the database is Miniflare's SQLite, not Cloudflare's D1, and there is no `request.cf`. The review of migration 0014 left open whether Cloudflare's D1 behaves identically for NUL text and BLOB `json_valid`; this launcher does not answer that either.
7. **No hosting-level protection beyond the gate.** No rate limit, no bot protection, no log shipping, no alerting. The gateway logs one line for a refused or failed request (never a header, a body or a credential).
8. **The launcher imports TypeScript directly** (`.ts` from `.mjs`), which Node 22.18 and later do without a flag; the image pins Node 22.22.0. A Node older than 22.18 will not start it.
9. **The header rule exemption.** `modules/platform/tests/static/source-rules.test.ts` now exempts exactly two files, `modules/hosting/src/gate.ts` and `gateway.ts`, from the rule that code reads only allow-listed headers: they run in a Node process in front of the Worker, they read `Authorization` as the gate's own password, and they must pass every other header on. A test fails if anything the Worker runs refers to them. That is an edit to another module's test, and the pull request says so; it touches the identity rule, so the pull request is labelled `needs-human-review`.
10. A dead Worker restarts the container, and a false alarm resets the demonstration. If workerd is killed, the gateway stays up (`/healthz` 503 within two seconds, every other page 502) and, since 6 October 2026, the launcher exits with code 1 about 30 seconds later (run: killed the Worker, the launcher left with code 1 after one log line; VALIDATION.md). That helps only on a platform that restarts a stopped container, which is assumed and was not run on DigitalOcean. A restart rebuilds the practice data, so a Worker that is merely very slow for 30 seconds in a row (six probes, each timing out after 2 seconds) would reset a demonstration in progress [Likely not on 1 vCPU with 300 MB in use; not measured under load]. A Worker whose health route answers 503 (a missing guard trigger) is treated the same way. `APLYD_WATCHDOG_PROBES=0` turns it off.
11. A restart resets the data but not the sign-ins: a session cookie issued before the restart is still accepted after it, because `SESSION_SECRET` is unchanged and the seeded people keep their ids (checked on 6 October 2026).
