# Run module: status

Owner: the run module. Paths: `modules/run/`, `app/run/`, `app/api/companies/[id]/engagements/[eid]/outcomes/`, and migrations 0012 and 0013 in `drizzle/`. It also adds a "Results" link on the home page and a test-only `exec` helper to `modules/platform/tests/support/worker.ts` (see Known limits). Last updated 5 October 2026 (the page rebuilt, slice 10c).

This is slice 6, Run: once the owner has accepted work (slice 5), they record a baseline (what the thing they were fixing was like before) and look again 30, 90 and 180 days after the first acceptance: the number now, whether it did what the assessment expected, and whether it is still in use. The page also names the next idea in the owner's plan that has no requirement yet. Protected paths touched: data scope (a company's measurements, read and written only by that company's owner) and migrations (one append-only table and nine guard triggers). A separate agent has not yet read this slice; see [VALIDATION.md](VALIDATION.md). No person has read it.

**Nothing here measures anything.** Every number is one the owner types. The provider does not sign in (OQ-13) and sees nothing. The expected range comes from the opportunity library, which is SYNTHETIC: its figures are placeholders, so "did it do what was expected" compares an owner's number with an invented range. Nothing here touches money or the listing fee (D-03).

## What works

- **A baseline.** On `/run`, for each engagement the owner has chosen, one whole number, the state of things before the work, with an optional note. It is recorded once, and only before anything is accepted (a delivered or rejected milestone does not close it; an acceptance does). After that the page says no baseline was taken and offers none.
- **Three reviews.** Review 1, 2 and 3 fall due exactly 30, 90 and 180 days after the first acceptance (assumptions, REVIEW_DAYS in `src/state.ts`; a test keeps the migration's day counts equal to it). Before its day a review is not offered and the page shows the date it opens; from its day it can be recorded, however late. Each is recorded once and they are independent: the last can be recorded before the others. A review is a whole number (0 to 1,000,000,000), whether it did what the assessment expected (met, partly, not met), whether it is still in use, and an optional note (500 characters).
- **The change since the baseline** is the latest review's number less the baseline, in the unit the assessment used. "Latest" is the highest review number recorded. The page does not say whether the change is good or bad: which way is better depends on the measure.
- **What the assessment expected** is shown beside the numbers: the measure, the unit, and the range, copied from the assessment the requirement came from, tagged SYNTHETIC on the page and with `synthetic: true` in the data (the assessment says so; the flag is read from it, not written here).
- **The next idea.** The first idea the owner accepted in the same assessment that has no requirement yet, in the assessment's order, with a link to `/procure`. An idea whose requirement was withdrawn counts as asked and is passed over, because a withdrawn requirement cannot be made again (procure limit 9) and the link would lead to a refusal. Nothing is made for them.
- **The scope rule** is the platform's own. Another company's owner, and the operator, get a 404 identical to a missing record, audited (`outcome.read.denied`, `outcome.write.denied`). A person in the company who is not its owner may read and gets 403 on any change. Every query is bound to the signed-in person's company, and a static test checks every SQL string on the table and that only the data layer touches it (the one statement of the data layer that names `engagements`, the insert's check that the engagement is the company's, is allowed by the deliver module's static rule, in that shape only).
- **The clock is the application's.** Days are counted from timestamps the application writes (dates on the page are UTC, and the page says so), and the database refuses a review whose stamp is before the due time (a trigger), so the page cannot be used to open a review early. Handlers take an optional clock so a test can stand at day 29 and day 30. If either timestamp cannot be read as a time, the review is refused, not let through.
- **Form posts** that fail once the person is known (a bad number, a step that is refused, an engagement of the company that does not exist) go back to `/run` with a message, never a page of JSON; the JSON interface gets JSON for the same. A form post refused *before* the person is known is answered with JSON, as in slices 3 to 5 (they use the same shared platform check, `authorizeCompanyWrite`): no session (401), another company named in the path (404, the same body as a missing record), the operator (404), a request another website started (403) and a body over 64 KB (413). The page's own form posts only to the signed-in company's path, so only an expired session reaches it in practice, and then the person sees a page of JSON (limit 13). Corrected 6 October 2026 (slice 11d): a form post with no valid session is now answered with a 303 to `/sign-in?expired=1`, decided in one shared place (`notSignedIn` in `modules/platform/src/api/http.ts`); a program that sends JSON still gets 401. The other refusals before the person is known stay JSON. A test pins each of these answers. An earlier version of this sentence said "never a page of JSON" without the exception; the independent review found it.
- **Append-only, in the database.** `outcome_events` refuses UPDATE, DELETE and any INSERT that would replace a row, on the id and on both partial unique keys (one baseline per engagement; one review per number per engagement). Six rule triggers enforce whole numbers (a figure and a review number, because the columns keep 1.5 as 1.5 and a range check lets it through), once-only, before-acceptance, needs-an-acceptance and due-date. The shape of each kind is a CHECK that names every column a kind needs as NOT NULL as well as in range (a CHECK that comes out NULL passes: the first version let a review with no verdict into the table by direct SQL, found by a test written for it). Every write also writes an audit entry in the same batch, only when a row was added.
- **D-03.** The table holds the owner's measurements and no fee, share, commission or money column. A static test pins the column list and checks that nothing in the module reads the listing fee, the listing terms or a provider's listing, and that no query aggregates measurements across companies.

## The page after the interface rebuild (slice 10c)

`/run` ("Results") was rebuilt on the shared interface of slice 10 (`app/globals.css`, `app/_ui/`, [the interface guide](../../docs/design/INTERFACE-GUIDE.md)). Behaviour did not change: the same forms post the same fields to the same endpoints, the `?saved=` and `?problem=` keys are the same, and every message, label, button name and test id that a test finds the page by is the same. What changed is what a person sees.

- **The top of the page** shows the five steps (Measure underlined), the one-sentence lede, the sentence that every number is typed by the owner and nothing on the page measures anything (visible, in its words; the browser test reads it), and one card on where things stand: a tag ("Your turn" or "Nothing to do now") and one sentence ("2 reviews are open now.", "Write down your starting number before the first milestone is accepted.", "Nothing needs you today. The next review opens on 2026-11-04."). When it is the owner's turn the card has a link ("Go to review N" or "Go to the starting number") to the place, an in-page anchor with no script.
- **Each engagement is a card** with its title, provider, cluster and a bar with "N of 3 reviews recorded", and then three blocks in order. **What was expected** shows the assessment's range in a tinted line, in the same words, with its SYNTHETIC tag. **Before the work** shows the starting number (large) with when it was recorded and the owner's note, or the form to record it with its one main button, or the existing explanation that none was recorded and none can be added now; a tag says Recorded, Your turn or Not recorded. **After the work** says when the first milestone was accepted (or that nothing has been), says the reviews are 30, 90 and 180 days after that day and that dates are in UTC, then shows the numbers and the three reviews.
- **The numbers are three small tiles** when there is something to show, which is once a review is recorded: the starting number (if there is one), the latest number and its review, and the change since the starting number (if there is a starting number). There is no chart and no word for good or bad: the sentence "Whether that is better or worse depends on what is measured; this page does not say." is under the tiles, in its words.
- **The reviews are three cards down a line**, each with a tag (Waiting, Not open yet, Open now, Recorded). A waiting or not-yet-open review is one tidy row with what is going to happen to it ("Starts when you accept your first milestone.", "Opens on 2026-11-04."). A review that is open now has the form, with one main button (when two are open at once, the first is the main one; `firstOpenReview`). A recorded review shows the two tags and the number, as before. The "Next in your plan" line is kept, with its link to the page that makes a requirement.
- **The long paragraph of caveats** that opened the page is in two places, in the same words: what concerns the numbers sits next to them (the typed-number sentence at the top, the 30, 90 and 180 days and UTC under "After the work"), and the sentence that the expected range comes from an assessment whose figures are placeholders, with the day counts being assumptions and dates being in UTC, is in a collapsed "About these numbers and dates" card below the main action. A smoke test reads that sentence in the page's HTML, where a collapsed card is present.
- **Logic that was added** is in `src/view.ts` and tested in `tests/unit/view.test.ts` (9 tests): the tag of each review state, the latest recorded review, how many are recorded, the state of the whole page in one sentence, the first open review, and where the owner's turn is. Nothing in it judges a number.
- **No script runs on the page.** It is server-rendered with plain forms, and has its own small stylesheet (`app/run/run.css`, every class prefixed `ru-`).

## Not built

- **Anything for the provider.** No sign-in, no view of the results, no way to dispute a number.
- **Measuring.** No reading from a machine, a sheet or an app; no check that a number is plausible, current or the same measure as the baseline.
- **Comparing a result with the expected range** as better or worse, or turning the verdict into a score.
- **Reminders.** Nothing tells the owner a review is due; they see it when they open the page.
- **Correcting a review's verdict or its answer on use.** Only the number is corrected (slice 11b). A baseline or a review is still never edited or replaced.
- **More than three reviews, or a different schedule.** The three day counts are fixed.
- **Aggregates.** No count or average across companies; any such figure would need the five-company floor (C-04) and does not exist.
- **Acting on the next idea.** It is a link.
- English only; no export or print.

## Known limits

1. **The number is the owner's word.** Nothing checks it, and the baseline is taken by the same person whose purchase it judges. A baseline typed after the work is not caught, only a baseline typed after an acceptance is recorded in the application (OQ-08).
2. **The expected range is invented.** It comes from the SYNTHETIC library. A "met" or "not met" against it is not evidence of anything.
3. **Day counts are assumptions** (30, 90 and 180) and are counted from the first accepted milestone, not the last, nor from the date the provider says it finished.
4. **The database trusts the application's time.** The due-date trigger compares the stamp the application wrote with the first acceptance's stamp; anyone who can write to the database with a stamp of their own can open a review early. Only the application writes here, and the Worker's clock is the only clock it uses.
5. **Which unit** a number is in is the assessment's, shown beside the box; the owner can type a number in any other unit and nothing notices.
6. **"First accepted" is final.** An acceptance cannot be undone in slice 5, and its table is append-only, so the date the reviews count from cannot move. If a later slice lets an acceptance be reversed, this slice's day counts have to be looked at again.
7. **The next idea ignores prerequisites and cost.** It is the next accepted idea in the assessment's order; whether it is sensible after what was just done is not looked at.
8. **A test-only database helper.** `exec` on the test Worker harness runs SQL against the throwaway database to add events dated in the past. It is in `tests/support`, not in the application, and a page or a request cannot reach it. The browser tests that use it add the events the application would have written on that earlier day; the database's triggers still apply.
9. The guards test and the health check confirm that triggers exist by name. They do not run them; the integration tests prove behaviour with real SQL, one probe per rule.
10. Two requests racing for the same step are decided by SQLite serialising writers and the triggers. A test sends them one after another inside one process. Two Workers racing were not run.
11. Denied attempts write audit rows without a cap, as everywhere (platform limit 8).
12. The page was run in Chromium only, against a local Worker, with a synthetic sign-in. The inherited platform limits apply.
13. **(Fixed 6 October 2026, slice 11d: a form post with no session now redirects to the sign-in page with a message; see line 18.) An expired session shows a page of JSON on a form post.** The shared platform check answers 401 before the form is read, and the page has no way to turn that into a redirect. The same is true of slices 3 to 5, which use the same check, so their STATUS claims about form posts carry the same exception (corrected on the review-fixes branch). A fix belongs in the platform (an `isForm` argument to the shared checks, or a wrapper in each handler) and is not made here.
14. **The page and the API differ on who may read.** A person in the company who is not its owner may read through the API; `/run` shows them "This page is for the owner". Not a leak.
15. **The page does more work than it needs.** For each engagement it reads the company's requirements, the assessment and its digest, with no cap on the number of engagements (one per requirement). Fine at the sizes the synthetic data has; not measured at more.
16. **A JSON body may send the figure as digits in text** (`"17"`), as a form does; the review number must be a number. Deliberate (a test says so), and inconsistent: noted by the review.
17. **Dates are UTC.** The day a review opens is the UTC day of the first acceptance plus 30, 90 or 180 days, to the millisecond; an owner in India may see a date a day off from theirs, and the form appears at the exact instant, not at the start of the day.
18. **A run note is bounded by a CHECK that counts with `length()`** (`outcome_events_note`, 500 characters), and SQLite's `length()` stops at a NUL character: a direct insert of `a`, a NUL and more text would be stored whole (found by the review of the review fixes, for the notes of earlier slices; the same is true here). The handler counts characters and refuses control characters, so the application cannot write it; migration 0014 bounds the earlier slices' notes in bytes too and does not cover this table.
19. **A correction is the owner's word too.** Nothing checks that the corrected number is righter than the first; the reason is free text. Both stay on record, which is all the BRD row asks.
20. **The guard list of the health check does not list the seven triggers of migration 0015.** `modules/platform/src/db/guards.ts` belongs to the platform module and was not changed by this slice, so `platform/unit/guards` fails on this branch until the platform owner adds them, and the health check does not yet notice if one is missing. The exact change is in the slice's report.
21. **The drizzle snapshots of 0012 to 0014 hold an older text of the CHECK `outcome_events_shape`** (without `IS NOT NULL`; migration 0012 was edited before it was published and its snapshot was not). `drizzle-kit generate` therefore wrote a rebuild of `outcome_events` into 0015; the rebuild was removed by hand (it would have dropped the table's triggers) and the 0015 snapshot holds the CHECK as the database has it. A person who runs `pnpm db:generate` on an older snapshot chain would meet the same rebuild.
22. **A baseline posted by a stale form after the engagement was closed** gets `baseline_closed` from the handler, which reads the engagement first; the database's own answer to a direct write is the same. Between the handler's read and the insert, a close by another request is caught by the trigger, not by the handler.

## Slice 11b (6 October 2026): the starting number only while it means something, and corrections

Built by an agent at the sponsor's instruction; no person has read it. Protected path touched: a database migration (0015).

- **No starting number for an engagement that is closed or whose plan is not agreed (FND-253).** `presentOutcomes` offers the form only when the plan is agreed, the engagement is open, nothing is accepted and no number is recorded (`baselineBlock` in `src/state.ts`; the reason is in `baselineBlocked`). Results then says which it is instead of the form: "Agree the plan on Delivery first. Then record the starting number here, before the first milestone is accepted." (tag "Not yet") or "This engagement was closed before any milestone was accepted, so there is no starting number to record." The top sentence and the link to the owner's turn follow, because they read `canRecordBaseline`. The page and the home page's rule (`modules/journey/src/progress.ts` `canRecordBaseline`) now agree.
- **Refused at the handler and in the database.** A baseline posted for a closed engagement gets 409 `baseline_closed` (a form: `/run?problem=baseline_closed`, "This engagement is closed, so a starting number cannot be recorded for it."); one posted before the plan is agreed gets `baseline_no_plan` ("Agree the plan on Delivery first. ..."). Nothing is written and nothing is audited. Migration 0015 adds two triggers on `outcome_events` that refuse the same rows for whoever writes (`outcome_events_baseline_not_after_close`, `outcome_events_baseline_needs_an_agreed_plan`); the data layer names their refusals the same way. No existing trigger was changed. Their conditions are written not to overlap with the six of 0013: a second number is still "recorded once" and a number after an acceptance is still "too late", closed or not.
- **Correcting a number (BR-RUN-09).** Under a recorded starting number or review, a collapsed "Correct this number" form takes the right number and why the first was wrong (required, up to 500 characters). It posts `kind=correction` to the same endpoint (API-21) and appends a row to the new table `outcome_corrections` that names the row it corrects. The row it corrects is never changed. The latest correction of a row is its current value: the large number, the tiles and the change since the starting number use it. The page shows the first number struck through with the tag "Corrected", and each correction with its date and reason; an earlier correction that a later one replaced is struck through too. A correction can be corrected by another; all stay.
- **A correction is the company's and the engagement's own.** The insert checks, in the same statement, that the row it names is a number of this engagement of this company; otherwise nothing is written and the answer is 404 (`/run?problem=missing`), the same as for a row that does not exist. A trigger (`outcome_corrections_names_an_outcome`) refuses the same for any writer, and a composite foreign key ties the row to the company's engagement. The table is append-only (three triggers) and refuses a figure that is not a whole number (a trigger) and a reason that is empty or over 500 characters or 2,000 bytes (a CHECK). Each correction writes an audit entry, `outcome.corrected`, with the engagement and the corrected row, in the same batch.
- **What is not corrected.** A review's verdict and its answer on use, the dates, and the notes. A correction is allowed whether or not the engagement is closed (a typing slip can be found late).

The limits this slice adds are 19 to 22 under Known limits.

## Slice 12d (6 October 2026): the shared "your turn" card, and a starting-number refusal that does not talk about reviews

Built by an agent at the sponsor's instruction (wave 2); no person has read it. The database rules and migrations were not changed.

- **One "your turn" card at the top (S5-06, S5-17).** Results passes its in-page places to the shared frame: the first starting number that can be recorded (`#bl-<engagement>`) and the first open review (`#rv-<engagement>-<n>`). When the journey's `nextStep` is one of these, its card is drawn directly under the page head with its button on the form, and the page's own summary card is not drawn. When the owner's turn is on another page, the summary says "Nothing on this page needs you today. Your next step is on another page: “<title>”, at the foot of this page." instead of "Nothing needs you today" (`resultsSummary(list, elsewhere)` in `src/view.ts`, unit-tested).
- **A refused starting number (S5-16).** A form post of a starting number whose only fault is the number now goes to `/run?problem=baseline_invalid` (was `invalid`). The message names the unit of the idea's measure when every engagement that can take a number uses the same one: "That could not be saved. The starting number box takes a number only, in percent: for example 42, not “42 late orders”. Give a whole number from 0 to 1,00,00,00,000." It says nothing about reviews. Any other fault (a review field on a baseline) keeps the general message. The JSON answer is unchanged. The box still takes digits only: "42" is recorded, "42 late orders" and "42%" are refused.
- **The eyebrow** reads "Step 5 of 5: Measure". **Colours:** each `color-mix()` in `run.css` has a plain colour before it, and `.ru-expected` and `.ru-next` use the darker muted tint.
- **Left as they were:** dates on Results stay YYYY-MM-DD, because the journey and demonstration browser suites (owned by others this wave) pin "Opens on YYYY-MM-DD" and "You first accepted a milestone on YYYY-MM-DD". A redirect after a post still lands at the top of the page (S5-10 not done).
