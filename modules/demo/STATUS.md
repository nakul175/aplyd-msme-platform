# Demo module: status

Owner: the demo module. Paths: `modules/demo/`, the route `app/demo/page.tsx` (it only renders this module's script), and a small change to `scripts/serve.mjs` (the hosting module's launcher: it now hands the application its demonstration flag and calls this module's seeder). Last updated 5 October 2026.

This is slice 9, stacked on slice 8 (the hosting launcher). It is a presenter-led demonstration of what the platform does today, in the manner of the Saha demonstration package: a seeded cast of invented people at different points in the journey, a script for a presenter, and a way to start again. It is SYNTHETIC from end to end and shows no real company, person, provider or figure.

## What it is

- **A cast.** Five invented companies (C to G) and their owners, added to the platform's own two (A and B) and its operator. C is the finished example: described, assessed, signed off, asked for the first idea, chose a provider, agreed a two-milestone plan, recorded a starting number, accepted and recorded a payment for the first milestone, and has the second milestone delivered and waiting. D has an agreed plan; E has chosen a provider and written no plan; F has asked for two ideas and chosen nobody; G has asked for one. Company A has only its confirmed description, so the presenter can walk it live; B has nothing, to show it sees none of the others.
- **Seeded through the application's own requests.** `src/seed.ts` signs in as the operator and as each owner over HTTP and does what they would do on the pages: set the fee, add and list three providers, describe, confirm, make and sign off an assessment, ask for ideas, choose a provider, add milestones, agree the plan, record a baseline, a delivery, an acceptance and a payment. Every check the pages meet is met and every step is an audit entry. The one exception is the people (`src/identities.ts`: `INSERT OR IGNORE` of companies and users, as the platform's seed does), because there is no sign-up (OQ-13).
- **The floor of five, shown on purpose.** Five companies ask for the first idea in the first cluster, so a company that joins sees "at least 5". Three ask for the second idea in the second cluster, so a company that joins is the fourth and the page says the number is not shown. The seeder checks this on the operator's pool list and refuses to finish if it is not so.
- **A script on `/demo`** (`src/script.ts`, `app/demo/page.tsx`): eight steps, about 15 minutes, each with who to sign in as, where to start, what to do and what to point out, then a list of what the demonstration does not show and how to start again. The page exists only in demonstration mode (`APLYD_DEMO=true`); elsewhere `/demo` is not found.
- **Starting again is a restart.** The database is rebuilt at every start of the launcher, so the demonstration is back to its starting state, and anything entered in a presentation is gone. The tables are append-only, so nothing can be put back by deleting rows; there is no reset button, on purpose.

## The page after the interface rebuild (slice 10c)

`/demo` was rebuilt on the shared interface of slice 10. It is not an owner's page, so it has no five steps: it opens with the page head, the SYNTHETIC note (a note, not an alert) and the sentence about signing in. **The people** are a card each (name, company, a tag for how far the company has got, the story). **The walk** is a card per step: its number and title and its minutes as a tag, a short list ("Sign in as", "Open", where "Open" names the home-page link the step starts from), "What to do" as a numbered list, and "What to say" as a quotation. Then what the demonstration does not show, and how to start again. Every string comes from `src/script.ts` and `src/cast.ts`, which were not touched; the static test that every label the script names is in the page sources and that the home page offers every link the script opens from passes unchanged. The one wording change is on the page, not in the script: "Sign in as X, then open Y." became the two lines "Sign in as" and "Open". The page has its own small stylesheet (`app/demo/demo.css`, every class prefixed `dm-`) and runs no script.

## How to run it

`APLYD_DEMO=true` with the launcher's other settings (modules/hosting/STATUS.md): `SESSION_SECRET=… DEMO_USER=… DEMO_PASSWORD=… APLYD_DEMO=true node scripts/serve.mjs`, after `pnpm build`. On DigitalOcean App Platform add `APLYD_DEMO` with the value `true` to the app's environment. The launcher says "The demonstration was added: 5 companies, 3 providers, N requests." when it has finished; until then the address answers 503 "starting".

## Not built, and limits

1. **It shows what the application does today, not the thesis.** There is no voice, no photo, no owner's own language, no provider sign-in, no money, no real compliance rule, no review by a second person. The script says so on the page.
2. **The 30, 90 and 180 day reviews are shown as dates only.** A review opens on its day and the application's clock cannot be moved by the pages; the run module's own test dates an acceptance in the database to reach one. The demonstration does not do that: nothing here writes outside the application's requests, apart from the people.
3. **The cast is five similar garment units.** They share their answers' shape (the same problems and the same sector) so the diagnosis ranks the same two ideas first and the pools form; a unit test pins that against the engine. It does not show how the ranking changes for a different factory: the diagnose module's tests do.
4. **Anyone who can sign in can sign in as anyone.** That is synthetic sign-in (OQ-13). On a hosted address the launcher's gate is the only protection (modules/hosting/STATUS.md, limit 1).
5. **The placeholder fee is shown to the operator** (₹1,500) and to no owner (a smoke and a browser test check this, `/demo` included, and a unit test checks the script never states it: D-03). No fee is decided (OQ-11).
6. **The seeder cannot be run twice on one database.** The append-only tables refuse a repeated description, assessment or plan, so the second run stops at the first refusal and names it. It is meant for a database that was just built.
7. **A change to a page's wording can break the script.** A static test looks for every button and field the script names in the pages' sources, and a browser test follows the whole script; a changed label fails them, which is how a renamed button is meant to be noticed, and also what makes them brittle.
8. **The seeder takes the application's own slowness.** On the development machine it makes about 100 requests in a few seconds; on a small hosted container it was not timed.
9. **Cross-module edits.** `scripts/serve.mjs` (hosting) and `modules/platform/tests/static/source-rules.test.ts` (platform) are changed in this slice: the launcher passes the flag and calls the seeder; the header rule's exemption list gains the seeder's HTTP client (`modules/demo/src/client.ts`, which reads the one response header that sets its session) and its test now follows imports and fails if the Worker can reach any exempt file. The pull request says so. The test layer for the demonstration reuses the hosting module's launcher support (`modules/hosting/tests/support/launcher.ts`).
