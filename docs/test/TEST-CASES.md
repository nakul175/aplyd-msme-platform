# Test cases

Version 0.1. Date 5 October 2026. Status: draft, not reviewed by a person.

This document is the one copy of the test cases for the APLYD MSME platform. Each case is written against one or more business requirements in the [business requirements document](../brd/BRD.md) and says how it would be checked, at which layer, and whether a test that exists today already checks it. A case marked automated names a real test file and the exact title of a test in it; a check (section 2) opens the file and fails if the title is not there. Nothing in this document says that a requirement is accepted. Passing automated tests are evidence; acceptance is a person witnessing the criterion ([UAT plan](UAT-PLAN.md), section 1).

How this relates to the other documents: [test strategy](TEST-STRATEGY.md) says why the layers exist and how they run; [test scenarios](TEST-SCENARIOS.md) chain cases into journeys; the [regression pack](REGRESSION-PACK.md) says which cases run on which change; [traceability](TRACEABILITY.md) is generated from this table and the BRD; the [UAT plan](UAT-PLAN.md) covers the cases only people can run; [test data](TEST-DATA.md) says what data each case uses. Functional requirements are not cited here: the functional specification was being written at the same time, and the traceability matrix has a column for the links to be added.

## 1. How to read a case

Every case is one row of a table under section 4. The columns are fixed, because the check reads them.

```text
| ID | Requirements | Title | Layer | Type | Steps and data | Expected result | Automation |
```

| Column | Meaning |
| --- | --- |
| ID | TC-AREA-NN. AREA is the area of the case's first requirement (GOV, ID, DESC, DIAG, PROC, DEPL, RUN, OPS, UX, DATA, COM, NFR). Numbers run 01, 02, 03 in each area with no gap. |
| Requirements | One or more BR IDs from the BRD, separated by commas. The first names the area. A requirement may appear in many cases. |
| Layer | Where the case runs: static, unit, integration, smoke, browser or manual. An automated case is in the layer of the directory its test file is in. Layers are described in the [test strategy](TEST-STRATEGY.md), section 2. |
| Type | positive (it should work), negative (it should be refused), boundary (a limit, tried on both sides), security (scope, identity, integrity), regression (a guard that must not be lost), usability (a person's understanding or an empty or waiting state). |
| Steps and data | What is done and with what. For an automated case this describes what the test does, as read from the test. All data is synthetic ([test data](TEST-DATA.md)). |
| Expected result | What must be true. It starts with Partly: when the named test covers only part of the case, and the text then says which part. It starts with Cannot be tested until when nothing that exists can run the case, and the text then says what must exist first. |
| Automation | Exactly one of three forms, described below. |

The Automation cell is one of:

- `automated: <repository path of a test file> :: <title of a test in it>`. The title is copied from the file, word for word. The runner is `node scripts/test.mjs`; see the [test strategy](TEST-STRATEGY.md), section 8.
- `designed`. The case is written so that someone could build it. No test file checks it today. It may be a command run by hand or in continuous integration, or a test not yet written.
- `people`. Only a person can run it, with an owner, an operator or a reviewer. The [UAT plan](UAT-PLAN.md) says how.

Two conventions keep the table honest. A requirement that nothing in the repository can yet exercise (voice input, a provider's sign-in, a revenue model) is covered by a row of layer manual, type usability, whose expected result starts Cannot be tested until and says what is missing. Such a row is a reminder, not a test. An automated row that starts Partly: counts as automated coverage in the matrix but never as full coverage ([traceability](TRACEABILITY.md), section 1).

Several rows cite the same test, because one test often checks several things. Where a test covers a limit, the Expected result states which values the test actually tries; a limit that a test does not try on both sides is said so, and a designed row sits beside it.

## 2. What the check enforces

`node scripts/check-test-docs.mjs` reads this table and fails if:

- a row is not well formed: eight cells, an ID of the form TC-AREA-NN, requirement IDs that parse, a known layer and type, an Automation cell of the three forms, a layer that matches the test file's directory, a Partly: or Cannot be tested until prefix on the wrong kind of row;
- IDs are repeated, or numbers in an area do not run in order;
- a case cites a requirement that is not in the BRD;
- a requirement in the BRD is cited by no case;
- an automated case names a file that does not exist, or a title that the file does not declare as the first argument of `test`, `it` or `describe`;
- a Must requirement that the BRD calls Built or Partial has no automated case and is not in the known-gaps block below, or the block lists one that has an automated case or is not such a requirement;
- the counts and the matrix in [TRACEABILITY.md](TRACEABILITY.md) are not what these rows add up to. Run `node scripts/check-test-docs.mjs --write` to regenerate them.

The check does not run the tests. That is the test runner's job ([test strategy](TEST-STRATEGY.md), section 8). It proves that the table points at tests that exist, not that the tests pass or that they check what the case says; the second is a matter of reading them, and the findings of that reading are in the [test strategy](TEST-STRATEGY.md), section 10.

## 3. Known gaps in automation

A Must requirement that the BRD calls Built or Partial should have at least one automated case. Three do not. The list is checked in both directions: a requirement may be here only while it has no automated case, so the list cannot go stale.

<!-- AUTOMATION-GAPS-START -->
- BR-NFR-04: evidence for every change lives in each module's VALIDATION.md. No test reads those files, so a module could lose its record without a test failing. The case is designed.
- BR-NFR-05: the regression guard (a missing suite, a missing baseline or fewer passing tests than the baseline fails the run) lives in `scripts/test.mjs` and runs on every full run. No test makes the guard fail on purpose, so its failure paths are unproven. The case is designed.
- BR-NFR-06: the seven-day release-age rule is in `pnpm-workspace.yaml` and is applied by the package manager. No test reads it, and there is no bill of materials or audit step. The case is designed.
<!-- AUTOMATION-GAPS-END -->

## 4. Cases

Cases are grouped by the area of their first requirement. A requirement in one area is often checked by a case in another, because one test checks several things; the [traceability matrix](TRACEABILITY.md) lists every case for each requirement.

Two notes on citing. First, the cross-site refusal of form posts (an Origin or Sec-Fetch-Site header from another website) is built and tested in every module, but the BRD has no requirement that names it. Those cases cite BR-ID-01 and BR-NFR-13, the nearest; the gap is reported to the BRD's owner. Second, cases that guard the vendor-neutrality invariant (D-03) and the floor of five (C-04) say so in their titles, so that a search for either finds them.
