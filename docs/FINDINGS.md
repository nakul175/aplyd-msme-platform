# Findings register: APLYD MSME platform

Version 0.2. Date: 5 October 2026. Status: draft, not reviewed by a person.

This register puts in one table every discrepancy, gap, review finding and known limit that another document of the repository already records. It adds no finding of its own, with the exception of the 34 rows that section 10 lists, which two agent reviews and a documentation pass recorded first; every other row points to the section that records it. Nothing in it has been accepted, and no person has read it. Every company, person, provider and figure in the application is SYNTHETIC.

How this relates to the other documents: the [documentation index](DOCUMENTATION-INDEX.md) says where each source document sits and which test checks it, and the [glossary](GLOSSARY.md) defines the terms used here. The sources are the status and validation pages of each module and the design, operations and test documents (section 6). The form of this register is checked by `modules/docs/tests/static/findings.test.ts`, which reads the reader in `modules/docs/src/findings.ts`.

## 1. What the register is, and is not

- It is a list of what the documents already say is wrong, missing, unproven or not known. Each row is one finding as its source states it, shortened to one line.
- It is not a new investigation. The test checks on the evidence only that the named file exists and, where a text is named, that the file holds it (section 5). Whether a finding is true today is what its source says. For version 0.2 the author also read the code that the rows about the pages and the journey module name, at commit f35b835, and corrected the rows that the code had overtaken. The other rows were not read against the code.
- It does not copy the BRD column "Status today" or the FSD rows marked TO BE. Those are the plan: a requirement that is not yet built is not a discrepancy. A decision (D-nn) or an open question (OQ-nn) appears in a row only where the source of that row names it; the decisions and questions themselves are in `docs/decisions.md` and `docs/open-questions.md`.
- One row can hold several points that its source lists together (for example "L10, L11"). One finding that several documents record is one row with several sources.
- One row, FND-268, states a contradiction between two documents and the code of which the cited source records only the code side. Its Evidence names the other side.

## 2. The columns

- **ID.** FND-nnn. An identifier is never changed and never reused, and a row is never deleted. A new finding takes the next number and goes at the end of its module's rows, so numbers rise within a module but not always down the whole page.
- **Finding.** One line, in plain words, as the source records it.
- **Evidence.** Where to look. A path from the repository root, and, after a colon, a name: text that the file holds, such as a function, a test title, a setting or a phrase of the source. Where the source names nothing to look at (the finding is that something is not known or not done), the cell says so.
- **Severity.** The word the source gives. See section 3.
- **Module.** The module whose status or validation page records the finding, or whose code holds the evidence: platform, factory, diagnose, procure, deliver, run, journey, hosting or demo (the directories under `modules/`). A finding about a shared file under `app/` goes under the module whose status page or tests name that file: journey for the strip, the next-step card, the home page and the contrast guard; platform for the root layout and the style sheet in general; procure for the operator page. A finding that no one module owns, such as one about the CI workflows, the process or the documents, is under repository. Rows are grouped by module in that order.
- **Source.** A link to the section of a document that records the finding. The first link is the place the row was written from. Links after the word "also" are other documents that record the same finding, and may use other words.
- **Status.** See section 4.

## 3. Severity

No severity scale is set down in the repository. The reviews used the words high, medium and low without a written definition, and the [test strategy, section 9](test/TEST-STRATEGY.md#9-defects-and-severity) proposes a scale marked TO BE. This register does not apply it and does not rate anything. A row carries the word its source gives, and "not rated" where the source gives none.

Read the "not rated" column before the "high" column. Severity comes mostly from the independent reviews recorded in the validation pages, and from a few known limits that state one. The other known limits and the discrepancy lists of the design documents do not rate. The counts of high, medium and low are therefore the counts of what a source rated; they are not a measure of how serious the open findings are.

## 4. Status

Every status starts with one of four forms. A note in brackets after it is copied from the source.

- **open.** The source records the finding and none records a fix or a decision about it.
- **fixed in** and the slice, branch or commit. The source says a change was made. The register has not run the fix. Under the [test strategy, section 9](test/TEST-STRATEGY.md#9-defects-and-severity) a defect is closed when a test or a witnessed run shows it gone, and an agent's statement that it is fixed does not close one.
- **documented decision.** The source records that the behaviour stays as it is, and why, or that the figure is an assumption.
- **evidence changed: re-check.** A file or text that the row names as evidence is gone, so the row may be out of date. Section 5 says how a row gets this status.

## 5. Evidence and the re-check rule

Every path in the Evidence column must exist, and every name after a path must be text that the file holds (for a directory, text that a file under it holds). `modules/docs/tests/static/findings.test.ts` checks this on every run.

When the check fails because a file was renamed, deleted or reworded, the way to make it pass is not to delete the row. Start the status with "evidence changed: re-check" and say what is missing. A person then reads the source section and the code, and sets the status again. The row and its ID stay.

To add a finding: write the row at the end of its module's rows with the next number, link the section that records it, and replace the counts block with the one the test prints. To close one: change its status and leave the row. The register is edited by hand; no script in the repository writes it.
